# Model Context Protocol `2026-07-28` — normative wire values

This document transcribes the normative wire values of MCP revision `2026-07-28`: every
JSON-RPC method string, `_meta` key, error code, HTTP header, result-envelope literal,
capability shape, extension identifier, deprecated-registry row and MRTR rule, copied
from the protocol's own artifacts. The primary source is the 3197-line
`schema/2026-07-28/schema.ts`; the generated `schema.json` and the specification
prose supply the MUST/SHOULD requirements the schema cannot express. `2026-07-28` is a
stateless, MRTR-based revision: `initialize` and `ping` are removed, `server/discover` is
the only server-MUST RPC, capabilities moved to per-request `_meta`, and every
server-to-client interaction (sampling, elicitation, roots) is a value inside
`InputRequiredResult` rather than a top-level JSON-RPC request.

- Research date: 2026-09-29
- Contract: [`../../PROTOCOLS.md`](../../PROTOCOLS.md) — the normative wire values
- Evidence: this file, transcribed from the artifacts named per table

`CancelledNotification` appears in **both** unions. Restriction, verbatim from
`schema.ts`: *"On stdio, the server also sends this notification, solely to terminate a
`subscriptions/listen` stream… Servers MUST NOT use this notification to cancel any other
request."* From `patterns/cancellation.md`: *"A server **MUST** send
`notifications/cancelled` referencing a `subscriptions/listen` request ID when it tears

**not** in it, and that is what the declarations in
[`mcp-2026-07-28-schema.md`](mcp-2026-07-28-schema.md) §10 establish: five of the
eight carry a **required** `params` naming their own interface, and the three
`list_changed` notifications carry `params?: NotificationParams` — optional, and
that interface's single member is an optional `_meta`. Every one of the eight
inherits that `_meta` from `NotificationParams`, which no row above mentions.

Key-name grammar, verbatim: the prefix is *"a series of labels separated by dots (`.`),
followed by a slash (`/`)"*; labels *"MUST start with a letter and end with a letter or
digit; interior characters can be letters, digits, or hyphens (`-`)"*; *"Any prefix where
the second label is `modelcontextprotocol` or `mcp` is **reserved** for MCP use"* — so
`io.modelcontextprotocol/`, `dev.mcp/`, `org.modelcontextprotocol.api/` and
`com.mcp.tools/` are reserved, *"However, `com.example.mcp/` is NOT reserved, as the second
label is `example`."* The name: *"Unless empty, MUST begin and end with an alphanumeric
character (`[a-z0-9A-Z]`)"*; the interior may contain `-`, `_`, `.`.

Not `_meta` keys, despite living nearby:

- `x-mcp-header` — a **JSON Schema extension keyword** inside `Tool.inputSchema`
  properties.
- `_meta["ui/resourceUri"]` (flat, **@deprecated** in ext-apps) and `_meta.ui.resourceUri`
  (nested, current) — ext-apps only.

### Range ownership, verbatim from `schema.ts`

> JSON-RPC 2.0 reserves `-32000` to `-32099` for implementation-defined server errors.
> MCP partitions that range:
> - `-32000` to `-32019`: implementation-defined. Existing SDKs and implementations use
>   codes here for their own purposes; the specification will never define codes in this
>   sub-range, and receivers must not assign cross-implementation semantics to them.
> - `-32020` to `-32099`: reserved for error codes defined by the MCP specification. Every
>   code allocated here is recorded in this file. Codes are allocated sequentially starting
>   at `-32020` and proceeding toward `-32099`.

`basic/index.md` labels `-32000`–`-32019` as **"legacy"**: *"New codes **MUST NOT** be
allocated in this sub-range, and new implementations **SHOULD NOT** use codes from this
sub-range at all."*

Out of range: *"New error codes for purposes not defined by this specification **SHOULD** be
allocated outside the JSON-RPC reserved range (`-32768` to `-32000`)."* And: *"Errors that
are purely local to an implementation … are not currently assigned codes by this
specification."*

| --- | --- | --- |

| `-32042` | URL elicitation required (`2025-11-25` only) | Implementations of `2026-07-28` **MUST NOT** emit. |

### Renumbering record, verbatim (`changelog.md` Minor #12)

> Renumber the error codes introduced in this draft accordingly — `HeaderMismatch`
> `-32001` → `-32020`, `MissingRequiredClientCapability` `-32003` → `-32021`,
> `UnsupportedProtocolVersion` `-32004` → `-32022` — and add `HeaderMismatchError` to the
> schema, which previously existed only in transport prose.

Conflict to note for codegen: the **names** `HeaderMismatch` /
`MissingRequiredClientCapability` / `UnsupportedProtocolVersion` used in prose and in the
`error.data` sense differ from the **schema constant identifiers** `HEADER_MISMATCH` /
`MISSING_REQUIRED_CLIENT_CAPABILITY` / `UNSUPPORTED_PROTOCOL_VERSION`. Both spellings are
primary-source; they are the same three codes.

## 4. HTTP headers

Source: `https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md`
(all sections), plus `basic/authorization/index.md` and `changelog.md`. Casing is exactly
as written in the source.

| Header name (as written) | Direction | Requirement level | Notes |
| --- | --- | --- | --- |
| `MCP-Protocol-Version` | C→S | **MUST** — *"Every POST request to the MCP endpoint **MUST** include an `MCP-Protocol-Version` header."* | Value **MUST** match `_meta.io.modelcontextprotocol/protocolVersion`. Mismatch ⇒ `400 Bad Request` + `HeaderMismatch` (`-32020`). Unsupported or unknown version ⇒ `400 Bad Request` + `UnsupportedProtocolVersionError` (`-32022`). A server supporting pre-`2025-06-18` clients **MAY** treat an absent header as `2025-03-26`; a server not supporting such clients **MUST** reject. |
| `Mcp-Method` | C→S | **REQUIRED for compliance** — *"These headers are **REQUIRED** for compliance."* | Source field `method`. Required for **all** requests. |
| `Mcp-Name` | C→S | **REQUIRED for compliance** | Source field `params.name` **or** `params.uri`. Required for `tools/call`, `resources/read` and `prompts/get` only. If the source value cannot be safely represented as plain ASCII the client **MUST** Base64-sentinel-encode it. |
| `Mcp-Param-{Name}` | C→S | Client **MUST** support the feature; server **MUST** validate and **MUST** reject on mismatch | Derived from an `x-mcp-header: "<Name>"` annotation in `Tool.inputSchema`. `x-mcp-header` itself is **optional for servers** — *"While the use of `x-mcp-header` is optional for servers, clients **MUST** support this feature."* |
| `Mcp-Session-Id` | — | **REMOVED in 2026-07-28** | `changelog.md` Major #1. Legacy handling: *"An `Mcp-Session-Id` header on a request: ignore it, and do not mint or echo session IDs."* |
| `Last-Event-ID` | — | **NOT SUPPORTED in 2026-07-28** | *"Resumable SSE streams via `Last-Event-ID` are not supported."* `changelog.md` Major #9 removes SSE event IDs and message redelivery. Legacy handling: *"A `Last-Event-ID` header: ignore it; streams are not resumable."* |
| `Origin` | C→S | Servers **MUST** validate on all incoming connections (DNS-rebinding defense) | *"If the `Origin` header is present and invalid, servers **MUST** respond with HTTP 403 Forbidden. The HTTP response body **MAY** comprise a JSON-RPC *error response* that has no `id`."* |
| `Accept` | C→S | Client **MUST** — *"The client **MUST** include an `Accept` header listing both `application/json` and `text/event-stream` as supported content types."* | Applies to every POST. |
| `Content-Type: application/json` \| `text/event-stream` | S→C | Server **MUST** return one of the two | *"The client **MUST** support both."* |
| `X-Accel-Buffering: no` | S→C | Servers **SHOULD** | *"When initiating an SSE stream, servers **SHOULD** include the `X-Accel-Buffering: no` header."* |
| `Authorization: Bearer <access-token>` | C→S | **MUST** — *"authorization **MUST** be included in every HTTP request from client to server"* | *"Access tokens **MUST NOT** be included in the URI query string."* |
| `WWW-Authenticate` | S→C | Servers **MUST** (401) / **SHOULD** (403 `insufficient_scope`) | 401 example: `WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource", scope="files:read"`. 403 params: `error="insufficient_scope"`, `scope="…"`, `resource_metadata`, `error_description` (optional). Servers **SHOULD** include `scope` in the challenge. |

### `x-mcp-header` constraints

Verbatim, identical wording on `tools#x-mcp-header` and `streamable-http#schema-extension`.

- **MUST NOT** be empty.
- **MUST** match HTTP field-name token syntax (`1*tchar`, RFC 9110 Section 5.1).
- **MUST NOT** contain control characters, including carriage return (CR, `\r`) or line
  feed (LF, `\n`).
- **MUST** be case-insensitively unique among all `x-mcp-header` values in the
  `inputSchema`.
- **MUST** only be applied to parameters with primitive types (integer, string, boolean).
  *"Parameters with type `number` are not permitted."* Integer values **MUST** be within
  −2⁵³+1 to 2⁵³−1.
- **MUST** only be applied to properties *statically reachable* from the schema root via a
  chain consisting solely of `properties` keys. *"The chain **MUST NOT** pass through
  `items` (or any other array keyword), composition keywords (`oneOf`, `anyOf`, `allOf`,
  `not`), conditional keywords (`if`/`then`/`else`), or `$ref`."*

### Base64 sentinel header-value encoding, verbatim

```text
Mcp-Param-{Name}: =?base64?{Base64EncodedValue}?=
```

*"The prefix `=?base64?` and suffix `?=` … are case-sensitive and **MUST** appear exactly as
shown (lowercase)."* Triggered by non-ASCII, control characters, or leading/trailing
whitespace. *"clients **MUST** also Base64-encode any plain-ASCII value that matches the
sentinel pattern."* Servers **MUST** decode before comparing to the body.

Type conversion: `string` as-is; `integer` → decimal string; `boolean` → lowercase `"true"`
or `"false"`.

| Scenario | Client | Server |
| --- | --- | --- |
| Parameter value provided | MUST include the header | MUST validate header matches body |
| Parameter value is `null` | MUST omit the header | MUST NOT expect the header |
| Parameter not in `arguments` | MUST omit the header | MUST NOT expect the header |
| Client omits header but value is in body | Non-conforming client | MUST reject the request |

### Other HTTP mechanics

| Value | Level | Note |
| --- | --- | --- |
| `202 Accepted`, no body | Server **MUST** | For an accepted notification POST. |
| `400 Bad Request` | Server **MUST** | Header validation, unsupported version, missing required client capability, malformed request missing required `_meta`. |
| `403 Forbidden` | Server **MUST** | Invalid `Origin`; invalid or insufficient scopes. |
| `404 Not Found` | Server **MUST** | RPC method not implemented, with JSON-RPC body code `-32601`. |
| `401 Unauthorized` | — | Authorization required or token invalid. The `Authorization` header is **MUST** on every request, so 401 is the unauthenticated path. |
| `405 Method Not Allowed` | Server **SHOULD** | HTTP GET or DELETE to the MCP endpoint, when serving only `2026-07-28`. |
| Header *name* comparison | **MUST** be case-insensitive | *"Header *values* (such as method names) are case-sensitive."* |

Casing inconsistency to encode deliberately: the spec writes the version header as
`MCP-Protocol-Version` (all-caps `MCP`) but every other MCP-defined header as `Mcp-Method`,
`Mcp-Name`, `Mcp-Param-{Name}` (title-case `Mcp`). Both spellings appear verbatim in the
same document and both are REQUIRED. They are wire-equivalent under the spec's own
case-insensitivity rule, so a Zig header table must not key on one casing.

draft 2020-12 permits undeclared keys. The census is at
[`mcp-2026-07-28-schema.md`](mcp-2026-07-28-schema.md) §9 and the record is its
finding 11; `PROTOCOLS.md` §4.8.3 and §4.10.6 now say *declared* member set and mark

### `InputRequiredResult`, verbatim


| Field | Type | Required | Rule |
| --- | --- | --- | --- |

### `InputRequests`, verbatim

```ts
export interface InputRequests { [key: string]: InputRequest; }
export type InputRequest = CreateMessageRequest | ListRootsRequest | ElicitRequest;
```

Key: server-assigned string identifier. Value: one of exactly three request objects —
`ElicitRequest` (`method: "elicitation/create"`), `CreateMessageRequest`
(`method: "sampling/createMessage"`), `ListRootsRequest` (`method: "roots/list"`).
*"`inputRequests` values are request objects that **MUST** be one of `ElicitRequest`,
`CreateMessageRequest`, or `ListRootsRequest`."* And: *"A map of server-initiated requests
that the client must fulfill. Keys are server-assigned identifiers; values are the request
objects."*

### `InputResponses`, verbatim

```ts
export interface InputResponses { [key: string]: InputResponse; }
export type InputResponse = CreateMessageResult | ListRootsResult | ElicitResult;
```

Keys *"correspond to the keys in the `InputRequests` map; values are the client's result
for each request."* For each key in the previous `inputRequests`, *"the same key must
appear here with the associated response."*

| Member | Shape |
| --- | --- |
| `ElicitResult` | `{ action: "accept" \| "decline" \| "cancel"; content?: { [key: string]: string \| number \| boolean \| string[] } }` |
| `CreateMessageResult` | `extends SamplingMessage { model: string; stopReason?: "endTurn" \| "stopSequence" \| "maxTokens" \| "toolUse" \| string }` |
| `ListRootsResult` | `{ roots: Root[] }` |

Codegen note: none of the three `InputResponse` members extends `Result` and none carries
`resultType` — verbatim in the schema, and it differs from every other result in the
protocol.

### `requestState` — normative handling

| Role | Requirement, verbatim |
| --- | --- |
| Server | *"If a client request contains a `requestState` field, servers **MUST** treat `requestState` as an attacker-controlled input. If `requestState` influences authorization, resource access, or business logic, servers **MUST** protect its integrity (e.g. HMAC or AEAD) and **MUST** reject state that fails verification."* |
| Server (replay) | Inside the integrity-protected payload servers **SHOULD** include and verify on receipt: the authenticated principal; a short expiry (TTL); an identifier for the originating request *"e.g. the method name and a digest of its salient parameters"*. *"Integrity protection **MAY** be omitted only when tampering can cause nothing worse than request failure."* |
| Server (single use) | *"Servers for which a given `requestState` must be consumed at most once (e.g., one-time redemptions) **MUST** enforce that invariant server-side."* |
| Client | *"the client **MUST** echo back the exact value of that field when retrying the original request. Clients **MUST NOT** inspect, parse, modify, or make any assumptions about the `requestState` contents. If the `InputRequiredResult` does not contain a `requestState` field, the client **MUST NOT** include one in the retry."* |

### `InputResponseRequestParams`, verbatim

```ts
export interface InputResponseRequestParams extends RequestParams {
  inputResponses?: InputResponses;
  requestState?: string;
}
```

| Request type | Also extends / adds |
| --- | --- |
| `ReadResourceRequestParams` | `ResourceRequestParams` → `uri: string` |
| `GetPromptRequestParams` | `name: string`, `arguments?: { [key: string]: string }` |
| `CallToolRequestParams` | `name: string`, `arguments?: { [key: string]: unknown }` |

These three are the **only** request types that accept MRTR retry fields.

### Where MRTR is permitted

| Client request | Supports `InputRequiredResult` |
| --- | --- |
| `prompts/get` | Yes |
| `resources/read` | Yes |
| `tools/call` | Yes |
| any other client request | **MUST NOT** — *"Servers **MUST NOT** send `InputRequiredResult` responses on any other client requests."* |

### Remaining obligations

| Role | Requirement, verbatim |
| --- | --- |
| Server | *"Servers **MUST NOT** send an `inputRequests` that the client has not declared support for in its capabilities."* |
| Server | *"Servers **MUST NOT** assume that clients will fulfill the `inputRequests` or retry the original request."* |
| Client | *"If a client receives an `InputRequiredResult` that contains the `inputRequests` field, the client **MUST** construct the requested inputs before retrying the original request. If the `InputRequiredResult` does *not* contain the `inputRequests` field, the client **MAY** retry the original request immediately."* |
| Client | *"The JSON-RPC `id` **MUST** be different between the initial request and the retry, as they are independent requests."* |
| Client | *"Both the `inputResponses` and `requestState` fields affect only the client's retry of the original request. They **MUST NOT** be used for any other request that the client may be sending in parallel."* |
| Server | *"If additional, unexpected parameters are provided in the `InputResponses` object, the server **SHOULD** ignore any information it does not recognize or need."* |
| Server | *"If the client fails to send all the information requested in a previous `InputRequests` … the server **SHOULD** respond with a new `InputRequiredResult` requesting the missing information again, rather than returning an error."* |

## Cross-source conflicts and gaps

1. **Header casing.** `MCP-Protocol-Version` versus `Mcp-Method` / `Mcp-Name` /
   `Mcp-Param-{Name}` — same document, both REQUIRED, wire-equivalent under the spec's own
   case-insensitivity rule.
2. **Error-name spelling.** Prose names (`HeaderMismatch`,
   `MissingRequiredClientCapability`, `UnsupportedProtocolVersion`) versus schema constant
   identifiers (`HEADER_MISMATCH`, `MISSING_REQUIRED_CLIENT_CAPABILITY`,
   `UNSUPPORTED_PROTOCOL_VERSION`) for the same three codes.
3. **Capabilities placement in examples.** `basic/versioning.md` and
   `extensions/overview.md` show `{"capabilities": {...}}` unwrapped; the normative
   location is `_meta["io.modelcontextprotocol/clientCapabilities"]`.
   `extensions/overview.md` §Client Capabilities is the only example that shows the
   `_meta` form.
4. **`ui/*` method inventory.** The `2026-01-26` `apps.mdx` snapshot enumerates the `ui/*`
   methods inline in prose rather than in a normative table; the list is incomplete
   relative to the full SEP text. Marked `[UNVERIFIED]`.
5. **`application/a2a+json`.** Absent from every primary artifact checked (both schema
   files, the `llms.txt` page index, `changelog.md`). **NOT ESTABLISHED** for MCP
   `2026-07-28`.
6. **`io.modelcontextprotocol/tasks` missing from `client-matrix.md`.** It has a Stable
   versioned schema snapshot and is named in the core schema's own doc comments, but is
   absent from the official client-support matrix's identifier table.
7. **Static schema URL dead.** `https://static.modelcontextprotocol.io/schemas/2026-07-28/schema.json`
   returns HTTP 404. Use the `raw.githubusercontent.com` path.
8. **`ResultType` enum collapse.** `"complete" | "input_required" | string` means
   `schema.json` emits `resultType` as a bare `{"type": "string"}` with no enum. The
   two-value constraint is normative only in the TypeScript source and in `basic/index.md`
   §ResultType.
9. **`InputResponse` members lack `resultType`.** `CreateMessageResult`, `ListRootsResult`
   and `ElicitResult` do not extend `Result` and carry no `resultType`, unlike every other
   result type in the protocol.
10. **`server/discover` result type name.** The request is `DiscoverRequest`; the method
    lives under the `server/` prefix but the type is `Discover*`, not `ServerDiscover*`.
11. **Artifact line count, corrected.** This file previously recorded the
    `schema.ts` URL as *3203 lines*. It is **3,197** newline-terminated lines,
    98,426 bytes, ending with `| InputRequiredResult;` and a terminating

    `742750af0bb8c716e7030c4977c992b55d1adc4407e9e66997db5846baedc2cd`, which

# A2A 1.0.0 — normative wire values

This document is a verbatim transcription of the machine-readable artifacts that
define Agent2Agent (A2A) protocol version 1.0.0: the `specification/a2a.proto`
file at tag `v1.0.0`, and the rendered specification text where the proto
carries no annotation (JSON-RPC method strings, error codes, media types, IANA
registrations). Every table states its own `Source:` line. Values that no
primary source established read `NOT ESTABLISHED IN SOURCE` rather than
carrying a plausible guess. Where two primary sources disagree, both values
appear with a note.

### 5.3 Service parameters — the exact names

Source: rendered specification §3.2.6 "Service Parameters" (lines 576–587),
table verbatim.

| Name | Description | Example Value |
| --- | --- | --- |
| `A2A-Extensions` | Comma-separated list of extension URIs that the client wants to use for the request | `https://example.com/extensions/geolocation/v1,https://standards.org/extensions/citations/v1` |

Verbatim, immediately after: "As service parameter names MAY need to co-exist with other parameters defined by the underlying transport protocol or infrastructure, all service parameters defined by this specification will be prefixed with `a2a-`."

Version negotiation, §3.6.1 verbatim: "Clients MUST send the `A2A-Version` header with each request to maintain compatibility after an agent upgrades to a new version of the protocol (except for 0.3 Clients - 0.3 will be assumed for empty header)."

§3.6.2 verbatim: "Agents MUST process requests using the semantics of the requested `A2A-Version` (matching `Major.Minor`). If the version is not supported by the interface, agents MUST return a [`VersionNotSupportedError`](#332-error-handling)."

IANA header registrations, §14.2.1 and §14.2.2, verbatim `Header field name:`
values: `A2A-Version` and `A2A-Extensions`. Both `Applicable protocol: HTTP`,
`Status: Standard`, `Author/Change controller: A2A Protocol Working Group`.
`A2A-Version` related information: "The value MUST be in the format `Major.Minor` (e.g., \"0.3\")."

The version examples throughout the spec are `0.3` (lines 585, 2533, 3165,

### 6.3 `google.rpc.ErrorInfo` — `domain` and `reason`

**`domain` = `"a2a-protocol.org"`** — no scheme, no path. It is a domain
string, not a URI prefix. Stated identically in three places:

- §10.6, verbatim bullet: "`domain`: Set to `\"a2a-protocol.org\"`"
- §11.6, verbatim bullet: "`domain`: Set to `\"a2a-protocol.org\"`"
- §9.5 example (line 2775) and the §10.6/§11.6 examples: `"domain": "a2a-protocol.org",`

`@type` for the detail object, verbatim from §11.6: "`@type`: Set to `\"type.googleapis.com/google.rpc.ErrorInfo\"`". The §9.5 example uses the same string. §10.6 shows it in textproto form: `type: "type.googleapis.com/google.rpc.ErrorInfo"`.

`reason` rule, verbatim from §10.6 and §11.6: "`reason`: The A2A error type in UPPER_SNAKE_CASE without the \"Error\" suffix (e.g., `TASK_NOT_FOUND`)". §11.6 adds a second example: "(e.g., `TASK_NOT_FOUND`, `TASK_NOT_CANCELABLE`)".

**The rule is normative; only two `reason` values are written literally in the
spec.** The other seven are marked derived and follow from the stated rule.

| A2A Error Type | `reason` | Provenance |
| --- | --- | --- |
| `TaskNotFoundError` | `TASK_NOT_FOUND` | **verbatim**, 3 sources |
| `TaskNotCancelableError` | `TASK_NOT_CANCELABLE` | **verbatim**, 1 source (§11.6 e.g. list) |
| `PushNotificationNotSupportedError` | `PUSH_NOTIFICATION_NOT_SUPPORTED` | derived from the stated rule |
| `UnsupportedOperationError` | `UNSUPPORTED_OPERATION` | derived from the stated rule |

| `InvalidAgentResponseError` | `INVALID_AGENT_RESPONSE` | derived from the stated rule |
| `ExtendedAgentCardNotConfiguredError` | `EXTENDED_AGENT_CARD_NOT_CONFIGURED` | derived from the stated rule |
| `ExtensionSupportRequiredError` | `EXTENSION_SUPPORT_REQUIRED` | derived from the stated rule |
| `VersionNotSupportedError` | `VERSION_NOT_SUPPORTED` | derived from the stated rule |

`metadata`: "Optional map of additional error context" (§10.6). It is not
schema-constrained; the examples use ad-hoc keys. §9.5 example metadata:
`"taskId": "nonexistent-task-id", "timestamp": "2025-11-09T10:30:00.000Z"`.

`timestamp: "2025-11-09T10:30:00Z"`. §11.6 example uses camelCase:
`"taskId": "task-123", "timestamp": "2025-11-09T10:30:00.000Z"`. The two
examples disagree on key casing and on timestamp precision. §11.6 closing note
says "Extension fields like `taskId` and `timestamp` provide additional context
to help diagnose the error."

example; it is not stated normatively.

### 7.2 `signatures` exact shape

`signatures` is field 13, `repeated AgentCardSignature`, JSON name

verbatim: "Remove properties with default values from the Agent Card; Exclude the `signatures` field; Canonicalize the resulting JSON using RFC 8785 to produce the canonical payload". §8.4.1: "Before signing, the Agent Card content **MUST** be canonicalized using the JSON Canonicalization Scheme (JCS) as defined in [RFC 8785]."

- §9.4.6: "**Error:** Returns `UnsupportedOperationError` if the task is in a terminal state (`TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, or `TASK_STATE_REJECTED`)."
- §10.4.6: "Subscribe to task updates via streaming. Returns `UnsupportedOperationError` if the task is in a terminal state."
- `TaskNotCancelableError` (§3.3.2): "An attempt was made to cancel a task that is not in a cancelable state (e.g., it has already reached a terminal state like `TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, `TASK_STATE_CANCELED`, `TASK_STATE_REJECTED`)."

### 8.5 Terminal-state stream protocol, verbatim

§3.1.2 "Task lifecycle stream", full text: "**Task lifecycle stream:** If the agent returns a [`Task`](#411-task), the stream MUST begin with the Task object, followed by zero or more [`TaskStatusUpdateEvent`](#421-taskstatusupdateevent) or [`TaskArtifactUpdateEvent`](#422-taskartifactupdateevent) objects. The stream MUST close when the task reaches a terminal state..."

§3.1.2 "Message-only stream", full text: "**Message-only stream:** If the agent returns a [`Message`](#414-message), the stream MUST contain exactly one `Message` object and then close immediately. No task tracking or updates are provided."

§3.1.6, verbatim: "The operation MUST return a `Task` object as the first event in the stream, representing the current state of the task at the time of subscription. This prevents a potential loss of information between a call to `GetTask` and calling `SubscribeToTask`."

There is no `final` or `terminal` boolean field on `TaskStatusUpdateEvent`
(fields 1–4: `task_id`, `context_id`, `status`, `metadata`) and no done-marker.
A client detects stream end by transport close plus the `status.state` value.
`TaskArtifactUpdateEvent.last_chunk` (field 5) marks artifact completion but not
task completion.

## 9. Extension and binding namespace URI prefixes

### 9.1 The `a2a-` service-parameter prefix

Source: rendered specification §3.2.6, verbatim, complete sentence: "As service parameter names MAY need to co-exist with other parameters defined by the underlying transport protocol or infrastructure, all service parameters defined by this specification will be prefixed with `a2a-`."

The prefix is the **lowercase** string `a2a-`. The two concrete parameter names
are `A2A-Version` and `A2A-Extensions` (mixed case, as written in the §3.2.6
table and §14.2). gRPC normalizes to lowercase per §10.2.

### 9.2 Core protocol binding identifiers — not URI prefixes

Source: the `AgentInterface.protocol_binding` field. The proto comment (line
346), verbatim: "The core ones officially supported are `JSONRPC`, `GRPC` and `HTTP+JSON`."

The spec's §4.4.6 `protocolBinding` row repeats verbatim: "The core ones
officially supported are `JSONRPC`, `GRPC` and `HTTP+JSON`."

| Identifier | Written as | Where |
| --- | --- | --- |
| JSON-RPC binding | `JSONRPC` | proto comment, spec §4.4.6 |
| gRPC binding | `GRPC` | proto comment, spec §4.4.6 |
| HTTP+JSON/REST binding | `HTTP+JSON` | proto comment, spec §4.4.6 |

Note the spelling divergence: the identifier is `JSONRPC` (one word, no
separator) but the section heading and prose call the binding "JSON-RPC"; the
REST identifier is `HTTP+JSON` (with a plus sign) while the prose writes
"HTTP+JSON/REST". The identifier strings are `JSONRPC`, `GRPC`, `HTTP+JSON`.

A worked example in the spec (§4.6.1, lines 1305–1307) uses
`"protocolBinding": "HTTP+JSON"`.

**There is no namespace URI prefix for the three core bindings.** They are bare
tokens, not URIs. A search for an `https://` or `urn:` prefix on the core
bindings returns nothing.

### 9.3 Custom binding URI identifiers

Source: rendered specification §5.8 "Custom Binding Identification", verbatim:
"Custom protocol bindings **SHOULD** be identified by a URI. Using a URI as the
identifier provides globally unique identification across all implementers. The
`protocolBinding` field in the Agent Card's `supportedInterfaces` entry
**SHOULD** be a URI:"

The only example URI given, verbatim, §5.8 (lines 1562–1563 and 1570):

`https://example.com/bindings/websocket/v1`

And the breaking-change rule, verbatim: "When a breaking change is introduced to
a binding, a new URI **MUST** be used so that clients can distinguish between
incompatible versions:" followed by

`https://example.com/bindings/websocket/v1` to `https://example.com/bindings/websocket/v2`

This is an **example**, not a reserved namespace. `example.com` is IANA-reserved
for documentation. The spec does **not** define an A2A-owned binding-URI
namespace. The path shape `/bindings/{name}/v{n}` is demonstrated by the example
only and is **NOT ESTABLISHED IN SOURCE** as a convention — no normative sentence
mandates that shape.

§12.7 "Agent Card Declaration" repeats the example with a matching URL, verbatim:
`"url": "wss://agent.example.com/a2a/websocket"`, `"protocolBinding": "https://example.com/bindings/websocket/v1"`. §12.7 requirements verbatim: "1. **Transport Identifier**: Use a URI to identify the binding (see Section 5.8) 2. **Endpoint URL**: Provide the full URL where the binding is available". Note this §12.7 example omits `protocolVersion`, unlike the §5.8 example.

### 9.4 Extension URIs — example values only, no reserved prefix

The spec defines **no** A2A-owned extension URI namespace and **no** mandatory
prefix. §4.6.1 declares extensions by
`AgentCard.capabilities.extensions[].uri`, a free-form `string`.

The only extension URIs appearing in the spec are illustrative:

| Extension URI | Appears at |
| --- | --- |
| `https://example.com/extensions/geolocation/v1` | §3.2.6 table, §4.6.1 (twice), §4.6.2, §9.2, §10.2, §11.2, §14.2.2 |
| `https://standards.org/extensions/citations/v1` | §3.2.6 table, §4.6.1 (twice), §4.6.2, §9.2, §10.2, §11.2, §14.2.2 |

Both use the shape `{host}/{segment}/extensions/{name}/v{n}`. That shape is
**NOT ESTABLISHED IN SOURCE** as a convention — the spec states no rule.

Versioning rule, §4.6.3, verbatim: "Extensions **SHOULD** include version
information in their URI identifier. This allows clients and agents to
negotiate compatible versions of extensions during interactions. A new URI
**MUST** be created for breaking changes to an extension." And: "If a client
requests a versions of an extension that the agent does not support, the agent
**SHOULD** ignore the extension for that interaction and proceed without it,
unless the extension is marked as `required` in the AgentCard, in which case the
agent **MUST** return an error indicating unsupported extension. It **MUST NOT**
fall back to a previous version of the extension automatically." (The source's "a
versions" is a typo, reproduced verbatim.)

Extension declaration surface: `AgentCard.capabilities.extensions` (array of
`AgentExtension`), each with `uri`, `description`, `required`, `params`. Client
opt-in per the §4.6.1 example is the `A2A-Extensions` service parameter,
comma-separated. Per-message extension data is carried in `Message.extensions`
(field 7, `repeated string`) and `Artifact.extensions` (field 6, `repeated
string`), with the actual payload in the `metadata` Struct keyed by extension
URI — per the §4.6.2 examples: `"metadata": { "https://example.com/extensions/geolocation/v1": { "latitude": 37.7749, ... } }`.

### 9.5 The one A2A-owned URI namespace in the whole spec

Source: rendered specification §6.4, §14.1.1.

| URI | Context | Count |
| --- | --- | --- |
| `https://a2a-protocol.org/errors/version-not-supported` | §6.4 example `"type"` field of a problem-details error | 1 |
| `https://a2a-protocol.org/latest/specification` | §14.1.1 "Published specification" pointer; page metadata | several |

Neither is defined normatively. The `errors/` form appears once, inside an
illustrative example, and conflicts with the `google.rpc.Status` error shape used
everywhere else (§6.4 above).

The `google.rpc.ErrorInfo` `domain` is `a2a-protocol.org` — no scheme, no path.
It is a domain string, not a URI prefix.
